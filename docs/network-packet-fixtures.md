# Disposable network packet fixtures

Protected services-only and guest-only fixture profiles are now documented in the
[fixture extension](../tests/fixtures/network/README.md). That extension supersedes
the original allow-only profile boundary below; all historical evidence retains
its actual result. Parent-only execution and preservation requirements still apply.

`tests/fixtures/network/network_packet_fixture.py` is an original, standard-library Python fixture for parent-operated observations on a **new, unused Virmill NAT or lab network** in the approved disposable VM. It creates two temporary network namespaces and two veth pairs, then removes only those objects after checking their identities. It never creates, changes, restarts or removes the selected libvirt network. It does not start a guest, change host firewall rules or sysctls, install software, or configure a production host.

The implementation contributes packet-observer prerequisites for **NET-01, NET-02, NET-03 and NET-05** in the normative acceptance package, with narrow native address-shape validation relevant to **NET-06** prerequisites. It does not test host/VPN/planned subnet collision detection or automatic allocation. Namespace endpoints do not qualify real guest routing, persistent guest configuration, a guest with three NICs, physical networking, or a services-only firewall adapter. The current fixture accepts only explicit `hostAccess=allow`. Services-only execution is deliberately unavailable until the product has an applicable firewall implementation. Every report sets `fullNetworkAcceptance=false` and `guestOrHardwareQualification=false`.

### Native XML normalization regression

The parent reported that native002 created the selected lab, then the original program (`d9af29b160496a01ead222a88754dc45fe9998b8565ca900ce5bc1e9dd67f099`) refused before endpoint creation because libvirt omitted the default `ipv6="no"` attribute. The parent's supplied live shape had the UUID-bound trusted bridge with `stp="on"`, `delay="0"`, a generated MAC, and IPv4 `10.197.236.1/24` with DHCP range `10.197.236.2`–`10.197.236.254`; the creation marker remained unchanged and no guest ports were attached. The author did not obtain this observation through remote access. The original run/result remains parent-owned evidence and is not rewritten as a success.

The correction follows the already accepted `internal/backend/networkxml/match.go` normalization: omitted `ipv6` and explicit `no` are equivalent for this profile; an existing `<forward>` with omitted `mode` means NAT. An explicit empty, enabled, uppercase, whitespace-padded or unknown IPv6 value still refuses, as do IPv6 IP declarations and non-NAT forwarding modes. Omitted forwarding never turns a lab into NAT. Ordinary comments are accepted as nonsemantic; DTD/entity declarations and processing instructions remain refused. The lexical directive check conservatively also refuses directive-like text inside comments.

The review also checked all other matcher normalizations. The observer already reads omitted `family` as IPv4, namespace-expanded creation markers, generated bridge MACs, live connection counters, and omitted/default bridge attributes without a false refusal. A combined regression now exercises these forms with the equivalent netmask representation for NAT DHCP, lab DHCP and static lab. Prefix/netmask selection was tightened: both attributes together, inverted hostmask notation, noncontiguous masks and padded numeric prefixes now refuse. The exact live XML hash is still required; no identity, marker or binding check was relaxed. The Go matcher remains the parent's full intent/declaration check; this small observer does not reproduce that matcher or authenticate network ownership.

Before changing the program, this exact pure command reproduced the mismatches:

```text
/usr/bin/python3 -I -B tests/fixtures/network/test_packet_parsers.py \
  NativeGuardTests.test_known_libvirt_normalizations_preserve_the_selected_profile \
  NativeGuardTests.test_equivalent_netmask_does_not_allow_ambiguous_or_inverted_masks \
  NativeGuardTests.test_native_comments_are_nonsemantic_but_xml_directives_refused
  FAILED: 3 tests; 3 failing subcases and 4 error subcases; 0.004 seconds
```

The 24-test full-suite result above is the normalization post-fix check and includes those cases plus explicit enabled-IPv6/forwarding refusals. Native re-execution, IPv6 packet enforcement, host/VPN overlap handling and real guest routing remain separate parent qualification steps. The normalization correction changes no packet expectation, cleanup target, capability requirement or report-success boundary.

### Veth initialization and explicit alias regression

The parent reported that native003 reached `ip link add` with exit 0, but the constructor's `alias` argument did not produce `ifalias` on either endpoint. The fixture correctly refused ownership and retained the DOWN, unattached pair for guarded parent review. A subsequent parent cleanup initially refused before mutation because both generated MACs had changed after the first snapshot, although names, indices 10/9, reciprocal peer names and DOWN/unattached state remained stable. The parent later obtained matching stable snapshots and completed guarded cleanup; these historical failures and cleanup observations are parent-owned evidence, not rewritten fixture successes. The reported `99-default.link` and `NM_UNMANAGED=1` observations do not prove which actor changed the MACs.

The corrected command sequence is create without alias → inspect and fsync initial pair receipt → bounded `udevadm settle --timeout=5` → inspect and fsync settled pair receipt → explicitly set host alias → verify both endpoints → explicitly set peer alias → verify both endpoints. Only after those checks does the fixture set and verify its declared peer MAC and move that peer into its held namespace. Every mutation still has its command intent written first.

Both receipts require exact generated names, distinct positive kernel indices, veth kind, canonical unicast MACs, reciprocal peer references and DOWN/unattached state. Same-namespace `ip -j -d` output may represent the reciprocal peer as `link` with the other endpoint's name or as numeric `link_index`; each present form must match the same snapshot, and missing/conflicting references refuse. Initial aliases must be absent or empty. Across successful settling, names, indices, peer relationship and DOWN/unattached state cannot change; initial and settled MAC values are retained with `MACChangeCause=not_attributed`. Settling is a bounded wait for existing udev work, not a claim that later changes are impossible. Any MAC change after the settled receipt refuses subsequent alias mutation or cleanup.

If alias setting returns success without changing the alias, or its acknowledgement is lost, cleanup may remove the pair only when both still match their entire recorded identity and remain DOWN/unattached. Previously verified aliases must remain exact; only the current already-journaled alias transition may be either empty or the expected run-specific value. This exception ends once both aliases are verified. A failed settle permits cleanup only against the unchanged initial receipt. Unknown creation acknowledgement, missing receipt, changed names/indices/MACs/peer relationship, unexpected alias or unexpected attachment remains manual-review-required. No pair is identified only by a familiar name, and no unknown alias is overwritten. An ambiguous veth also prevents namespace deletion that could otherwise destroy a moved endpoint indirectly.

The ten new pure tests check exact create/set argv order, durable receipt ordering, observed initialization MAC transitions, same-namespace peer JSON forms, no-op and lost alias acknowledgements, loss of the original creation acknowledgement, failed settle with and without MAC drift, replacement/attachment changes during alias setup, index drift during settling, and post-receipt MAC drift before the first alias command. All 34 tests pass locally without running udev, creating namespaces, opening packet sockets or executing native commands. Actual operation remains a parent-only follow-up with the new source hash; this correction adds `udevadm` as a required installed prerequisite and does not weaken packet expectations.

### Forwarding-readiness gate and bounded DHCP diagnostics

The parent reported that native004 passed explicit alias setup, device settling and cleanup, but its nine-second DHCP OFFER phase timed out after two received frames and no malformed frames. Host dnsmasq logs reportedly recorded a DISCOVER and emitted an OFFER for the correct fixture MAC. These observations do not establish whether STP timing, reply timing or another packet-path issue caused the failure; the fixture does not assign a cause or rewrite the failed run as packet proof.

The current fixture waits after bringing up each generated endpoint and before DHCP/static setup. It reads only the owned host veth's `/sys/class/net/NAME/brport/state`, accepting state `3` as forwarding. The author verified `/usr/include/linux/if_bridge.h` using `rg -n '^#define BR_STATE_' /usr/include/linux/if_bridge.h`: disabled `0`, listening `1`, learning `2`, forwarding `3`, blocking `4`. That local header is 20938 bytes, SHA256 `becc49c81b632c9bd766620fd5cc5c85854af14c5abda99d4d7ea368381a9e7f`. Reading the header is not a native packet test.

The wait is at most 35 seconds, additionally constrained by the existing 180-second fixture deadline. It polls at most every quarter second, records at most 142 observed states with elapsed times, and writes `bridge-forwarding-a.json`/`bridge-forwarding-b.json` on success or failure. Each poll checks the recorded host ifindex, settled MAC, exact alias, master ifindex and bridge ifindex/MAC. Before and after waiting, the full host and namespace-peer identities, expected aliases/MACs, veth kind and administrative UP state are rechecked. Successful readiness also requires the unchanged native XML and bridge L3 observation. A missing field, unknown state, changed identity or timeout refuses before DHCP. No bridge option, forwarding delay or STP state is written, and a forwarding-state observation is not proof of a working DHCP exchange.

DHCP now allows 18 seconds for each OFFER/ACK phase and uses a 40-second subprocess timeout; other workers keep their 24-second subprocess limit. Retransmission remains bounded at three-second intervals. On failure only, the worker appends at most its first eight received-frame samples to the structured error retained by the command journal. Each sample retains at most 2048 bytes, the retained-byte SHA256, actual received/captured lengths, truncation/message flags, packet type, available EtherType/IP protocol/UDP ports/BOOTP XID and client MAC, and unrelated/malformed/matched-phase classification. Malformed reasons are limited to 256 characters. Samples are taken only from the already-owned fresh namespace peer, never a broad host capture. Success does not publish these unrelated-frame samples; correlated OFFER/ACK evidence remains unchanged.

Seven additional pure tests cover listening→learning→forwarding transitions, the 35-second timeout with retained states, identity drift after observing forwarding, exact sysfs identity checks, DHCP-only subprocess timeout extension, an 18-second timeout retaining only the first eight ignored frames, and sample truncation/packet-type bounds. The full 41-test result is local generated-data/mocked-I/O evidence. No STP wait, DHCP exchange or new native run was executed by the author.

## Parent execution boundary

Only the parent/operator may execute this fixture on the already authorized disposable VM. Required `--root` selects an existing, canonical, nonsymlink direct child of:

```text
<test-vm-home>/virmill-tests
```

The selected child is the parent's new isolated run directory, not an inferred historical run. Root-only, relative, nested, noncanonical, control-bearing and symlink paths are refused. No old run journal is touched. Before execution, the parent must create and identify the new network through Virmill's reviewed workflow, inspect its creation/job binding, and exclude concurrent network/guest/namespace mutations throughout the fixture window. A Virmill XML marker is checked as a structural prerequisite; it is not treated as an authority grant or proof of ownership. The explicit `--confirm-new-unused-network` records the parent's external ownership check. This fixture is not safe for adoption of an existing/shared network.

Required remote facilities are Linux network namespaces, nsfs bind mounts under `/run/netns`, veth and bridge support, root on the selected disposable host with `CAP_SYS_ADMIN`/`CAP_NET_ADMIN`/`CAP_NET_RAW`, access to read-only `qemu:///system` libvirt inventory, and these already installed binaries:

```text
/usr/bin/python3
/usr/bin/virsh
/usr/bin/ping
/usr/bin/ip (or /usr/sbin/ip)
/usr/bin/udevadm (or /usr/sbin/udevadm)
```

No DHCP client package or tcpdump installation is required. Distribution binary symlinks are resolved to root-owned, non-group/world-writable regular files and recorded with hashes. Selected source and output paths refuse symlink components. Workers run the same hash-pinned source using isolated Python (`-I -B`) and a fixed minimal subprocess environment. Worker entry refuses the calling host network-namespace inode and requires its generated peer interface alias before opening sockets.

The fixture requires an active, persistent, autostart-off network, exactly matching UUID-derived `virmill-UUID` and `vm` plus the first twelve lowercase UUID hex digits. It checks a version-1 creation marker, exact live XML SHA256, NAT versus no-forward lab shape, one private IPv4 subnet with room for two endpoints, expected DHCP mode, no static DHCP reservations, the bridge gateway/address/prefix, and an empty bridge port list. An existing port, identity mismatch or unavailable prerequisite causes refusal. It checks the bridge/XML again immediately before attaching each owned veth, and after cleanup. No physical interface is accepted.

Use a newly generated, canonical, nonzero run UUID for each attempt. Output must be exactly `ROOT/network-packet-RUN_UUID`; exclusive creation and retention make that run UUID single-use. A failed run is not retried with the same UUID or silently reused output. The source SHA is the reviewed program bytes. The XML SHA is the SHA256 of **exact stdout**, including the trailing newline, from this read-only command on the selected approved VM:

```text
/usr/bin/virsh --readonly -c qemu:///system net-dumpxml NETWORK_UUID
```

Parent invocation template; every uppercase placeholder must be resolved from the parent's reviewed inputs, not guessed:

```text
/usr/bin/python3 -I -B /ABSOLUTE/FROZEN/network_packet_fixture.py run
  --execute-reviewed --confirm-new-unused-network
  --root <test-vm-home>/virmill-tests/NEW_ISOLATED_RUN
  --recipe-sha256 REVIEWED_SOURCE_SHA256
  --run-id NEW_RUN_UUID
  --network-id NEW_NETWORK_UUID
  --network-xml-sha256 EXACT_LIVE_XML_STDOUT_SHA256
  --bridge vmLOWERCASE12HEX
  --kind nat --host-access allow --dhcp on
  --output <test-vm-home>/virmill-tests/NEW_ISOLATED_RUN/network-packet-NEW_RUN_UUID
```

The template shows argv on separate lines for review, not a shell script. Parent code should invoke a list of literal argv elements. Use `--kind lab --dhcp on` for managed lab DHCP. For the static lab profile use `--kind lab --dhcp off --static-a4 ADDRESS_A --static-b4 ADDRESS_B`; both addresses must be distinct ordinary unicast addresses in the exact native subnet and must exclude its network, broadcast and gateway. No prefix is included in these address arguments; the pinned native subnet supplies it.

For a DHCP-enabled network, static overrides are refused because the Virmill pool may cover every usable guest address. The fixture creates two locally administered MACs derived from the run UUID, acquires its own OFFER/ACK pairs, checks the offer before REQUEST, checks the ACK against that offer, and validates server ID, native pool, subnet mask and at least a 300-second lease before assigning each address to its own namespace. It rejects duplicate assigned addresses. It leaves only its own server-side lease records on the disposable network; it does not read or modify a DHCP lease file or send RELEASE for anyone else.

Optional probes require deliberate inputs:

```text
--dns-name APPROVED_NAME
--forward4-target APPROVED_IPV4_LITERAL --forward4-port APPROVED_TCP_PORT
```

`--dns-name` makes one bounded A query through the selected bridge's gateway only. The report separately says whether that server appeared in the fixture ACK. A recursive DNS query may cause upstream traffic; supplying the name is an explicit choice to run that query. Without this flag DNS remains `not_tested` even if DHCP advertised a DNS server.

The forwarding probe makes one bounded TCP connection to the explicit target and port, sending no application payload. The target must be outside the selected subnet. Only that target's `/32` route is added via the pinned gateway, inside namespace A. No default route is installed. The report labels this a fixture-supplied route, so it cannot be mistaken for a DHCP-installed guest default. NAT expects a connection; lab expects no connection. A failed connection has its errno/reason retained and does **not** prove filtering: an independently verified reachable target/control path is required for a later enforcement claim. No target means `not_requested`; no public address or Internet test is silently selected.

## Observations and interpretation

The two endpoints use their own lease addresses or approved static addresses. IPv4 ping tests peer reachability. A temporary TCP listener binds only the exact bridge IPv4 address and device on a kernel-selected port, confirms `SO_ACCEPTCONN`, and sends a run-specific token to namespace A. Success requires receipt of that token; the listener is stopped and closed before cleanup. Because this profile requires host access allow, failed access is a fixture failure, never fabricated services-only success.

DHCP evidence contains exact generated DISCOVER/REQUEST frames and the matched OFFER/ACK frames, checksums/hashes and decoded router/DNS fields. Lab passes the router-option check only when option 3 is absent and neither route option 121 nor 249 is present; unimplemented alternative route encodings do not establish suppression. NAT requires option 3 to contain exactly the pinned gateway and also refuses to interpret alternative route options. No advertised router, DNS or route is automatically applied. DHCP-off execution verifies static reachability but does not claim packet-level absence of a DHCP server.

Captured DHCP replies validate bounded Ethernet/IPv4/UDP/BOOTP framing and identity before their fields can be used. Duplicate options, overloaded options, fragments, malformed lengths, missing cookie/end/type/server, invalid router/DNS sizes and ordinary bad checksums are refused. Linux `PACKET_AUXDATA` checksum status is retained: veth may expose a checksum awaiting offload completion. Such a frame is labeled `kernel_partial`, not falsely described as a verified wire checksum; `kernel_valid` and full `wire` validation remain distinct. This is a narrow DHCP observer, not a complete RFC client, a packet-authentication scheme, or a parser for arbitrary PCAP formats.

IPv6 link-local addresses are observed after a bounded DAD wait. Where both endpoints have ready link-local addresses, a scoped IPv6 peer ping is attempted. The fixture sends a router solicitation from its own link-local address and observes up to five seconds of RA traffic only on that fresh peer interface. It validates direct ICMPv6 RA framing, checksum, hop limit 255, link-local source and bounded options, then reports router lifetime and prefix information. Extension-header RAs are explicitly outside the parser. No RA seen in that window is not proof of absence. No IPv6 sysctl is changed, and global/bridge forwarding and disable settings are read only for context.

The current native profile declares IPv6 disabled. Observed IPv6 link-local delivery or any accepted RA sets `ipv6DisabledContradictedByObservedTraffic=true`. An `ipv6="no"` XML declaration is not promoted to packet isolation. IPv6 external forwarding remains explicitly untested for this IPv4-only profile; a future reviewed IPv6 profile, explicit addresses/gateway/targets and packet controls are required. `ipv6IsolationProven` stays false. This distinction can make IPv4 checks pass while the overall fixture reports a policy discrepancy.

Reports retain individual observations even if an expectation fails. Final `scoped_checks_passed` requires the requested IPv4 checks, no observed contradiction to IPv6 disabled, and verified cleanup. This status still does not certify guest routing or unobserved IPv6 paths. `failed_or_policy_discrepancy` preserves errors and successful component observations. `manual_review_required` cleanup prevents a passed result and requires inspection of the original run; it never authorizes blind cleanup or retry.

## Retention, limits and cleanup

The output includes `invocation.json`, `prerequisites.json`, `preflight.json`, an fsynced `mutation-intent.json`, `commands.jsonl`, per-endpoint forwarding-readiness and DHCP evidence when applicable, `observations.json` and final `report.json`. The command journal records literal argv and intent before execution, deadline, return code, bounded stdout/stderr and interruption. Native replies are not shell-evaluated. Captured traffic is confined to the new peer interface: normally correlated DHCP/RA/DNS bytes and own generated packets, with at most eight bounded received DHCP-phase frame samples added on failure for diagnosis, never broad host captures.

Each native command has a deadline; the command/output journal has a 240-command and 8 MiB aggregate bound, 256 KiB per stream, and the normal command phase has a 180-second deadline. Each udev settle has a five-second tool timeout and seven-second subprocess deadline. Each bridge-port wait is at most 35 seconds within the fixture deadline, with at most 142 state records. DHCP has two 18-second phases per endpoint with at most 512 inspected packets each and a 40-second worker subprocess limit; RA has five seconds and at most 512 packets; Ethernet frames are at most 2048 bytes; DNS responses at most 4096 bytes; TCP and DNS operations have three-second socket deadlines. Cleanup gets a separate 60-second command opportunity. Any exhausted bound is a failure, not a success substitute.

Namespace names contain the full run UUID. Veth names use a short UUID component within Linux's interface-name length, and each host/peer receives an explicitly verified full run-UUID alias. After alias verification, cleanup compares each acknowledged host veth's recorded ifindex, exact name, settled MAC, alias and veth kind; the narrowly bounded pre-alias pair checks are described above. It confirms the names are absent after deletion. It compares each namespace's held nsfs device/inode against its nonsymlink name and requires no remaining processes before removing the name. It never kills an unrelated namespace process. A lost creation acknowledgement, replacement, unfamiliar object, PID, inability to inspect or cleanup failure is retained for manual review. Name checks and native operations are not an atomic compare-and-delete API; the parent must keep the explicitly exclusive window, including throughout initial device settling. SIGINT/SIGTERM attempt bounded cleanup. SIGKILL/power loss cannot guarantee cleanup; the durable intent and command journal identify objects for human review, not automatic replay.

The bridge, its addresses, native XML, global routes, firewall and network definition are never cleanup targets. The tool does not flush firewall rules, disable host IPv6, delete the selected network, destroy VMs, touch source media or inspect TPM/NVRAM/key/state bytes. The ordinary `ip netns` implementation may establish its standard `/run/netns` infrastructure; the fixture does not remove that shared infrastructure. Root privileges and native capabilities remain unqualified until the parent records an actual disposable-host run.
